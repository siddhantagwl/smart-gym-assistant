# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A deeper system overview (rest-timer rationale, sync semantics, sequence diagrams) lives in [ARCHITECTURE.md](ARCHITECTURE.md). Read it before making changes that touch the rest timer, the Google Sheets sync pipeline, or the exercise-library seed.

## Commands

```bash
npm install              # install deps (run once / after pulling)
npm start                # expo start — Metro + dev menu
npm run ios              # native iOS build via expo run:ios
npm run android          # native Android build via expo run:android (debug)
npm run android:release  # release-variant Android build (the APK the user installs)
npm run web              # web build (expo start --web)
npm run lint             # expo lint (eslint-config-expo flat config)
```

There is no test runner configured. Type-check via `npx tsc --noEmit` (strict mode is on).

The `reset-project` script in `package.json` references `./scripts/reset-project.js`, which does not exist — ignore it.

### Target platform

**This app is developed and tested on Android.** iOS scripts exist in `package.json` but are not the primary target. When reasoning about platform-specific behavior (background execution, notifications, permissions, OS lifecycle), default to Android specifics — Doze mode, battery optimization, foreground services, notification channels — not iOS app suspension semantics.

### Versioning

The Home screen shows `app.json` → `expo.version` at the bottom so the user can tell which build is on their device. **Bump this version on every meaningful change** before reporting work as done — don't wait to be asked. Follow semver:

- **patch** (`1.0.0` → `1.0.1`): bug fixes, copy tweaks, small UI adjustments
- **minor** (`1.0.1` → `1.1.0`): new features, new screens, schema additions
- **major** (`1.1.0` → `2.0.0`): breaking changes (DB wipe required, sync contract change, etc.)

Edit `app.json` `expo.version` as part of the same change. The user rebuilds the APK against this version, so an un-bumped version means they can't tell whether their device has the new code.

### Environment

`.env` is gitignored and holds these `EXPO_PUBLIC_*` vars:

- `EXPO_PUBLIC_GSHEETS_WEBHOOK_URL` — Apps Script Web App URL (required for any sync)
- `EXPO_PUBLIC_GSHEETS_SECRET` — shared secret sent in the POST body (required)
- `EXPO_PUBLIC_GSHEETS_SPREADSHEET_URL` — direct URL of the spreadsheet, optional. If set, Settings shows an "Open spreadsheet ↗" link that calls `Linking.openURL`. Independent of sync — sync works without it.

The first two must be present for `services/googleSheetsSync.ts` (sessions/exercises sync, restore, library sync) to run. `EXPO_PUBLIC_` is required because Expo only exposes vars with that prefix to runtime code, and these are inlined into the JS bundle at build time — missing values silently ship as `undefined`. `services/googleSheetsSync.ts` exports `isSyncConfigured()`; Settings renders a red "Sync not configured" banner when it's false, so a busted build is visible at a glance instead of presenting as mystery sync errors.

For local builds, `.env` at project root is read by Metro at bundle time. For EAS Build, register the same vars via `eas env:create` (EAS does not upload your local `.env`).

Native `/ios` and `/android` directories are gitignored — they are regenerated by `expo run:*` and should not be committed.

## Architecture

### Layered model

```
UI (app/, components/)  ──reads──▶  SQLite (db/)  ◀──sync──▶  Google Sheets (services/)
                                       ▲
                                       └── domain/ (in-memory types)
```

Two principles drive almost every design choice — violating either is usually a bug:

1. **SQLite is the runtime source of truth.** Screens read directly from `db/*.ts` helpers (`db.getAllSync`, etc.). The UI never awaits the network during a workout.
2. **Sync is opt-in and asynchronous.** It runs on app boot (library only, if empty) or via explicit Settings actions. Network failure must never break logging.

### Bootstrap sequence

`app/_layout.tsx` blocks rendering until DB is ready:

1. `initDb()` from [db/schema.ts](db/schema.ts) creates the three tables (`sessions`, `exercises`, `exercise_library`), runs `ensureColumn()` ALTER migrations for older DBs, and calls `seedExerciseLibrary()` from the hardcoded list in `db/seedExercises.ts` (idempotent — uses `INSERT OR IGNORE`).
2. `setDbReady(true)` — only then does the Stack mount.

Returning `null` while not ready is intentional. Don't render fallback UI here; the goal is to guarantee no screen reads from an uninitialised DB.

There is no automatic library sync on boot. `seedExerciseLibrary()` only fills the table on first install (idempotent). The user runs `syncExerciseLibrary()` manually from Settings to pull the canonical library from Google Sheets.

### Routing

Uses `expo-router` with file-based routing and `typedRoutes` experiment on (`app.json`).

- `app/(tabs)/` — the four tabs: `index` (Home), `history`, `exercises`, `settings`
- `app/session-details.tsx` — modal presentation (configured in `app/_layout.tsx`)
- `app/manual-session.tsx`, `app/exercise-details.tsx` — stack screens

### Domain vs. stored types

This split is deliberate and load-bearing — preserve it when adding new fields:

- `domain/session.ts`, `domain/exercise.ts` — in-memory shapes used by UI/business logic. Dates are `Date` objects.
- `db/sessions.ts:StoredSession`, `db/exercises.ts:StoredExercise` — persistence shapes. Dates are ISO strings, JSON columns (`session_labels`, `tags`) are stringified.

Mapping happens at the DB-helper boundary. UI components should consume domain types; DB helpers translate.

### DB helpers

All SQL lives under `db/` — never inline `db.runSync` in components. Conventions:

- Synchronous APIs throughout (`expo-sqlite`'s `*Sync` methods). The codebase relies on this — don't switch to async helpers without a reason.
- Multi-statement writes (manual-session insert, sheet restore, library replace) use explicit `BEGIN; … COMMIT; / ROLLBACK;` blocks.
- "Raw" inserters (`insertSessionRaw`, `insertExerciseRaw`) exist for restore paths that bypass domain mapping. Don't use them from UI flows.
- `getRecentSessions` filters out `note = '__DISCARDED__'` — that sentinel marks soft-deleted sessions.

### Sync semantics (read before touching)

Two sync flows, both in `services/googleSheetsSync.ts`:

- **Sessions + exercises** (SQLite → Sheets, `syncToGoogleSheets`): full snapshot POST; the Apps Script handles dedup by ID. Restore (`restoreFromGoogleSheets`, GET no-param) is a non-destructive merge: inserts Sheet sessions/exercises whose ids aren't on the phone (`insertSessionRaw` / `insertExerciseRaw`) and copies the Sheet's `gym` onto matching sessions; it never deletes or otherwise overwrites phone rows. Restore does **not** touch `exercise_library`.
- **Exercise library** (Sheets → SQLite, `syncExerciseLibrary`): GET `?type=library`, full-replace inside a transaction (`replaceExerciseLibrary` in `db/exerciseLibrary.ts`). Sheet is authoritative; locally added entries are wiped on next sync. The hardcoded seed in `db/seedExercises.ts` only fills the table on first install via `INSERT OR IGNORE` — once the user runs library sync, they're effectively replacing the seed.

Both sync flows require `EXPO_PUBLIC_GSHEETS_WEBHOOK_URL` + `EXPO_PUBLIC_GSHEETS_SECRET`.

### Rest timer (non-obvious)

The rest timer in `components/ActiveSession.tsx` is **timestamp-based**, not countdown-based. `restStartRef.current = new Date()` is the single source of truth; everything else (visible counter, scheduled notification, saved rest seconds) is derived from it.

Three cooperating pieces, all keyed off `restStartRef`:

1. **Visible counter** (`restSeconds` state) — recomputed each `setInterval` tick as `duration - secondsBetween(new Date(), restStartRef.current)`, **not** decremented. So when Android suspends JS in the background and the interval pauses, returning to the foreground snaps the counter to the correct elapsed value within ~1s. Don't refactor this back to `prev - 1` — that's the broken pattern we replaced.
2. **Rest notifications** — `showRestNotifications()` in `services/notifications.ts` posts a "resting" notice immediately (`rest-status-v2` channel: HIGH importance so it pops up, but no sound/vibration; title "Rest 2:30", body exercise + next set — the user asked for just the timer, no clock time or loads) and schedules the alert at `+duration` seconds (`rest-timer-v2` channel, long ~2s vibration), both under the fixed identifier `"rest"` so the alert replaces the notice, plus a nudge (`"rest-nudge"`, "Rest +0:30 · Set N") 30s after the timer ends. The alert fires regardless of JS thread state (app backgrounded, screen off, app killed). Both are normal (not ongoing) notifications so watch apps (the user has an Amazfit Bip 6 via Zepp) forward them — keep the text short. Two kinds: `"set"` (type-based target, "Rest done · Set N") and `"transition"` (switch timer, "Next exercise"); durations, nudge, button and vibration come from Workout preferences. `stopRestTimer()` calls `clearRestNotifications()` (cancel + dismiss both ids); all calls go through a serial queue so a stop followed by a start can't remove the new notice — invariant: only one rest's notifications at any time. Channel vibration/importance can't change after creation — bump the channel id (`-v2`…) and delete the old one instead.
3. **Saved rest value** — `stopRestTimer()` computes `secondsBetween(new Date(), restStartRef.current)` and accumulates into `accumulatedRest`. Independent of whether JS was running. Finalized only on Start Set / Finish Exercise / manual close. The previous countdown-based implementation lost data and produced 0-second rests under race conditions — see ARCHITECTURE.md §3.2.

**Notification setup:** `setupNotifications()` in `services/notifications.ts` is called once on app boot from `app/_layout.tsx`. It registers the Android channels — `rest-timer-v2` (alert + nudge: HIGH, long vibration, default sound) and `rest-status-v2` (start notice: HIGH, silent) — deletes the superseded `rest-timer` / `rest-status`, and requests notification permission. If notifications never show, check the app-level permission first (`adb shell dumpsys notification` → `importance=NONE` means blocked) — `setupNotifications` gives up silently when Android won't ask again, so Settings shows a red "Rest notifications off · Open settings" line (`restNotificationsEnabled()`: app permission off or the `rest-timer-v2` channel switched off), re-checked on tab focus and when the app returns to the foreground. Idempotent. The module also calls `Notifications.setNotificationHandler` at module load to allow notifications to show even when the app is foregrounded — without this, `expo-notifications` suppresses everything while the app is on screen.

**Live countdown notification:** on Android the "resting" notice is posted natively by `modules/rest-live` (`RestLive.post`, called from `showRestNotifications`; expo fallback elsewhere) — ongoing, system chronometer counting down to the rest's end, public on the lock screen, and requested as an Android 16 Live Update (`android.requestPromotedOngoing` extra + `POST_PROMOTED_NOTIFICATIONS`). It uses tag `"rest"`, id 0 — the slot expo uses for identifier `"rest"` — so the scheduled alert replaces it and `dismissNotificationAsync("rest")` clears it. On the user's Samsung (One UI 8.5) Android sets `PROMOTED_ONGOING` but One UI doesn't show third-party apps in the status-bar chip / Now Bar; the countdown ticks in the shade and lock screen, and Zepp still forwards it to the watch.

**Notification buttons (+30s / Skip rest):** on the live countdown (native actions → launch intent with an extra, picked up by `RestLive` via `OnNewIntent` / foreground, emitted as `onRestAction` + `consumeAction()`) and on the alert + nudge (expo category `rest-actions`, `opensAppToForeground`). `services/restActions.ts` merges both into `subscribeRestActions`; ActiveSession applies them — Skip = in-app Skip rest (`stopRestTimer(true)`), +30s = `startRestTimer(max(target+30, elapsed+30), kind, details, sameStart)` so saved rest stays wall-clock correct. Stale taps are dropped (native 60s, expo 15 min). Rest state isn't persisted across process death, so a tap after Android killed the app just opens it.

**Mini floating timer (PiP):** `modules/rest-pip/` is a local Expo native module (Android only, autolinked from `./modules`). `startRestTimer` calls `armRestPip(endsAt, label, kind)`, `stopRestTimer` (and ActiveSession unmount) `disarmRestPip()`. While armed, leaving the app (home / recents) puts MainActivity into picture-in-picture (`setAutoEnterEnabled` on Android 12+, `OnUserLeavesActivity` on 8–11). JS is paused in PiP, so the window shows a **native** overlay — a `Chronometer` counting down to `endsAt` (amber for sets, grey for switch, red past 0) — added on top of the RN root and removed when PiP ends. `modules/rest-pip/app.plugin.js` (in `app.json` plugins) sets `supportsPictureInPicture` and adds `smallestScreenSize` to `configChanges` — without it entering PiP recreates the activity and reloads JS. Changing the Kotlin needs a native rebuild, not just Metro.

**Exact alarms:** `app.json` declares `android.permission.USE_EXACT_ALARM` (auto-granted on Android 13+; fine for a sideloaded APK, though Play restricts it to alarm/timer apps). Without it, `expo-notifications` falls back to an inexact alarm (`setAndAllowWhileIdle`) and Android delays the rest-done alert by minutes — the alert must fire when the timer hits 0.

**Android battery optimization caveat:** Android's Doze mode can delay scheduled notifications by 10-30+ seconds when the device is idle (screen off, in pocket — exactly the rest scenario). To get on-time delivery, the user must set the app to "Unrestricted" battery in system Settings. We don't request the `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` permission programmatically; that's a documented one-time per-device setup. The breathing-cat ring animation (`Animated.timing` on `restRingProgress`) is also JS-driven and will visually drift on long backgrounds — known cosmetic, not blocking.

### Volume-down = set button

`modules/volume-keys` (local Expo module) wraps the activity window's `Window.Callback` to swallow `KEYCODE_VOLUME_DOWN` and emit `onVolumeDown` while enabled. `AddExercise` enables it via `captureVolumeDown` only while its screen is focused (`useFocusEffect`) and `isExerciseActive`, and routes presses to `onSetButton` (Start ↔ Finish Set, 700ms debounce, haptic). Volume-up and every other state keep normal volume keys; key events only arrive while the app is on screen.

### Workout preferences

`app/preferences.tsx` (Settings → ⚙ Workout preferences) edits `services/preferences.ts`: typed `Prefs` with `DEFAULT_PREFS` (the old hardcoded values), stored as JSON in the SQLite `preferences` table (`db/preferences.ts`, phone-only, not synced) and cached in memory. Read with `getPrefs()` (sync — rest timer, notifications, services) or `usePrefs()` (components, re-render on change). Covers rest targets per type (`restTargetFor(tags, restTargetsOf(prefs))`), switch timer, nudge seconds (0 = off), +N button, alert vibration (one channel per pattern: `rest-timer-v2` long, `rest-alert-short`, `rest-alert-pulse`), and switches for the rest-start notice, floating timer, volume-down, gym auto-detect, heart-rate line, plus the weekly target (History dots + widget). Don't hardcode these values again — add a pref.

### Gym auto-detect (GPS)

`services/gymLocation.ts` (expo-location, foreground only). `learnGymLocation(gym)` runs on Start session: asks for "while using" location the first time, takes a fix (≤100 m accuracy) and averages it into `gym_locations` (`db/gymLocations.ts`, phone-only, not synced) — skipped when a *different* known gym is within 250 m, so a wrong pick doesn't teach the wrong spot. `detectGym()` runs on Home focus when idle and returns the known gym within 250 m; Home preselects it with a green "auto" tag on the 📍 pill. A manual pick wins for 2 hours. Both skip when the phone's Location toggle is off (`hasServicesEnabledAsync`) — a fresh fix with location off makes expo-location show Google's "Turn on device location" dialog, which used to pop on every Home visit.

### Native modules

Local Expo modules live in `modules/` (autolinked, Android only, JS wrappers no-op elsewhere): `rest-pip` (floating timer), `rest-live` (live countdown notification + buttons), `volume-keys`, `home-widget` (4×1 "this week" widget: `WeekWidgetProvider` renders M–S dots from `{"yyyy-mm-dd": sets}` that `services/homeWidget.ts` pushes on boot and on every app → background; the week is computed natively at render, hourly, so it rolls over without the app; Start → `sadhana://`, dots → `sadhana://history`), `health-connect` (read-only: heart rate avg/peak/readings + total/active kcal for a session, over the overlapping watch workout — Zepp "Free training" — else the session times; shown by `components/WatchHeartRate.tsx` in Session details as "♥ ≈ avg · peak bpm · kcal", long-press for details. Sadhana writes nothing to Health Connect so Samsung Health has no duplicate workouts. Zepp shares ~per-minute HR, so avg/peak are a few bpm off the Zepp app — hence ≈; kcal matches exactly. Permissions are granted once via the "♥ Show heart rate from your watch" link; HC needs the rationale activity + `VIEW_PERMISSION_USAGE` alias in the module manifest or the dialog won't open). Kotlin changes need a native rebuild (`./gradlew assembleRelease` in `android/`), not just Metro. Their `android/build/` output is gitignored.

### Path alias

`@/*` maps to repo root (`tsconfig.json`). Use it for all cross-directory imports — e.g. `@/db/sessions`, `@/components/AddExercise`.
